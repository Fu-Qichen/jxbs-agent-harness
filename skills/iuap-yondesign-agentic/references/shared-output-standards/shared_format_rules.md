# 共享输出规范 — 格式文档

本节详细说明所有共享格式化函数的输出格式，供引用技能对照。

---

## 一、标题 emoji 规则（已废弃）

> 本规范已废弃。一级标题不再自动附加 emoji 前缀，emoji 的整体使用规则见 **第二十节 Emoji 基础规范**；代码侧 `h1()` 已不再输出 emoji。

---

## 二、概览统计格式

```
共 **N** 张订单，当前完工订单比例 **X.X%**，其中：

• 待审核：**N** | 开立或审核中的订单数量

• 在制中：**N** | 正在生产中的订单数量

• 已完工：**N** | 已完成生产的订单数量
```

- 数量 > 0 的分类项才显示
- 完工比例 = (finished + closed) / record_count × 100

---

## 三、分页提示格式

```
> 共**N**条数据，每页**20**条，当前第**X/Y**页。可回复[继续加载]或[第X+1页]查看更多
```

## 四、异常关注表格格式

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 逾期未开工 | **1** | 订单已超开工日期，尚未开工生产 |

数量为 0 的类别不显示。

## 七、v2.1.0 新增功能

### 7.1 表格自动序号列（规范 3.2 内容规则-1）

表格默认自动在首列添加序号列，序号从当前页起始序号计算。
领域若不需要序号，可在 schema 的 table 节中设置 `"show_seq": false`。

### 7.2 分割线条件判断（规范 3.8 禁止项-1）

`render_action()` 新增 `has_table` 参数，只有已渲染明细表格时才输出分割线。
`render_schema()` 自动跟踪 `has_rendered_table` 状态传入。

### 7.3 单列表项转普通句（规范 3.3 内容规则-3）

`render_suggestions()` 和 `render_summary()` 在仅有 1 项时自动转普通句，不再使用列表格式。

### 7.4 相对日期转实际日期范围（规范 3.4 日期格式-4）

`_resolve_relative_dates()` 自动将"今天""昨天""近7天""本月""本周"等相对日期标注为实际日期范围。
在 render_schema 的引言中自动执行此转换。

### 7.5 千分符防误伤（规范 3.4 千分符禁止项）

`_format_thousands()` 对 4 位纯数字且在 1000-2999 范围内的值跳过千分符（避免年份误伤）。

## 九、安全/合规底线规则（P0 — 所有输出必须遵循）

### 9.1 AI 状态区分（规范 4.1 状态一致-4）

AI 输出的建议、草稿、待确认动作、已执行结果**必须明确区分**，不得把建议/草稿表述为系统已执行结果。

| 状态类型 | 标注方式 | 示例 |
|---------|---------|------|
| AI 建议 | 以「建议」「可考虑」「推荐」开头 | ✅ "建议对 3 条逾期订单执行开工操作" |
| AI 草稿 | 标注「（草稿，待确认）」 | ✅ "已生成采购申请单草稿（草稿，待确认）" |
| 待确认动作 | 标注「待你确认后执行」 | ✅ "以下操作待你确认后执行：" |
| 已执行结果 | 直接陈述结果 | ✅ "已成功生成 1 张采购申请单，单号：CG20260710001" |

**禁止项**：
- ❌ 把建议写成"已执行"/"已完成"
- ❌ 在用户未确认时使用"已提交""已发布""已付款""已删除"等确定性动词

### 9.2 高风险动作确认规则（规范 4.1 风险动作一致-5）

以下动作**必须经用户确认后**才能执行或描述为已执行：

| 高风险动作类别 | 示例 |
|-------------|------|
| 写入/提交/发布 | 生成单据、提交审批、发布公告 |
| 付款/转账 | 发起付款、批量转账 |
| 删除/覆盖 | 删除订单、覆盖配置 |
| 授权/外发 | 权限授予、数据外发 |
| 关闭流程/批量变更 | 关闭工单、批量修改价格 |

**输出格式**：
```
⚠️ **需要你确认**：以下操作涉及 [动作类别]，请确认后继续。

• **「提交审批」**：将 3 张采购申请单提交部门经理审批
• **「批量变更」**：修改 12 条订单的计划完工日期

回复「确认」执行上述操作，或回复具体指令调整范围。
```

### 9.3 数据不足结构化说明（规范 4.6 数据不足说明-3）

当缺少关键字段、权限不足或时间范围不完整时，**必须输出结构化说明**，不得在数据不足时强行输出确定性结论。

**输出结构**：`不足说明 + 缺失清单 + 影响范围 + 补充动作`

**输出模板**：
```
⚠️ **数据不足，以下结论存在限制**

**缺失信息**：
• 缺少近 3 个月的销售数据，无法判断趋势（权限范围限制）
• [缺失字段]：[影响说明]

**当前可确认**：
• [基于已有数据可以确定的结论]

**补充建议**：
• 请补充 [缺失字段] 后重新查询
• 或联系 [角色] 获取 [数据范围] 的访问权限
```

### 9.4 错误反馈安全底线（规范 4.7 禁止项-6）

所有错误/失败反馈**绝对禁止**暴露以下内容：

| 绝对禁止 | 正确做法 |
|---------|---------|
| 堆栈追踪（stack trace） | "操作未能完成，请稍后重试" |
| 数据库密钥/连接串 | 不提及任何密钥信息 |
| 原始 SQL 语句 | "查询数据时遇到问题" |
| 内部接口参数 | "系统处理异常" |
| 内部服务名称/IP/端口 | "服务暂时不可用" |

**额外禁止**：
- ❌ 不得只显示"失败""异常""错误"等空状态词
- ❌ 不得把未成功的操作描述为"已完成"
- ❌ 不得在权限不足时泄露受限字段内容
- ❌ 不得使用"你操作错误""你权限不够"等归咎用户的表述
- ❌ 不得在无用户确认时自动重试高风险动作

**正确错误输出结构**：`简短说明 + 原因分类 + 恢复动作`

```
❌ [简短说明：操作未能完成]

原因：[系统异常 / 权限不足 / 数据冲突 / 外部系统不可用]（不暴露技术细节）

**可尝试的恢复动作**：
• [重试 / 补充信息 / 缩小范围 / 联系管理员]

已处理部分：[如有部分成功，说明已完成的内容]
```

## 十、整体业务规则（P1 — 所有业务输出必须遵循）

### 10.1 业务口径一致（规范 4.1-1）

涉及查询、统计、分析、推荐、判断时，以下口径必须明确：
- 筛选条件、时间范围
- 币种、单位、精度
- 组织范围、权限范围

多口径并存时，必须在输出开头说明本次使用的口径。

**输出模板**：
```
本次查询口径：时间范围 {start}～{end}，币种 CNY，单位 元，精度 保留两位小数，组织范围 {org_name}
```

### 10.2 数据来源一致（规范 4.1-2）

涉及查询/统计/分析/推荐/判断时，必须说明：
- 数据来源系统
- 查询时间/数据更新时间
- 数据范围

**不得在无来源、无口径、无时间范围的情况下输出确定性结论。**

### 10.3 输出分层一致（规范 4.1-3）

严格遵守双区输出模型的分层规则：

| 输出层 | 承载内容 | 不得承载 |
|-------|---------|---------|
| 会话区 | 摘要/结论/风险/操作建议 | 完整报告、宽表、单据全量明细、文件全文 |
| 右侧预览区 | 完整报告/宽表/单据/文件/图表/来源/计算逻辑 | — |

会话区中，完整业务明细应引导用户到右侧预览区查看，不得在会话区直接堆砌。

## 十一、引言规范（P1）

### 11.1 展示位置（规范 4.2-1）

引言**必须位于会话结果第一句**，在业务摘要、核心结论、结果明细、方案推荐等所有内容之前。

### 11.2 句式结构（规范 4.2-2）

引言固定句式为：**`状态/动作 + 来源或条件 + 对象 + 结果`**

| 场景 | 句式示例 |
|------|---------|
| 查询 | 已查询 {系统/模块}，在 {时间范围} 内，共找到 {N} 条 {对象} |
| 操作 | 已在 {系统/模块} 中 {动作}，{对象}，结果：{结果} |
| 分析 | 基于 {数据来源} 的 {时间范围} 数据，对 {对象} 进行分析 |
| 推荐 | 根据 {条件/规则}，为 {对象} 推荐以下方案 |

含相对日期时，必须标注实际日期范围（由 v2.1.0 相对日期转换自动完成）。

### 11.3 加粗规则（规范 4.2-3）

引言中**仅以下元素可加粗**：
- 查询条件中的关键筛选值
- 对象名称
- 核心数量
- 异常原因关键词

### 11.4 禁止项（规范 4.2-4）

- ❌ 不加粗整句话
- ❌ 不得在引言中输出核心结论、业务明细
- ❌ 不得堆砌字段列表
- ❌ 禁止使用"已完成处理，信息如下""查询结果如下"等无对象无结果的空泛句

**反例**：
- ❌ "已完成处理，信息如下："
- ❌ "已为你查询，以下是订单列表"

**正例**：
- ✅ "已查询生产订单模块，2026-07-01～2026-07-10 期间共找到 **12** 张订单，其中 **2** 张存在异常"

## 十二、核心结论规范（P1）

### 12.1 使用场景（规范 4.5-1）

出现以下情况时必须输出核心结论：
- 查询结果中存在明显重点、异常、排序、风险
- 业务分析/预测需输出趋势、差异、原因
- 推荐场景需输出首选方案和依据

### 12.2 展示位置与区块排序（规范 4.5-2）

| 场景 | 区块顺序 |
|------|---------|
| 有引言 + 核心结论 + 业务摘要 | 引言 → **核心结论** → 业务摘要 → 业务详情 |
| 有引言 + 核心结论 + 无业务摘要 | 引言 → **核心结论** → 业务详情 |
| 有指标概览 + 核心结论 | 引言 → 指标概览 → **核心结论** → 明细 |
| 有核心结论 + 异常关注 | 引言 → **核心结论** → 异常关注 → 明细 |

### 12.3 正常结论格式（规范 4.5-3）

句式：**`判断 + 关键依据 + 必要数值`**

使用场景：数据充分、来源可靠、结果明确且无异常时。

```
✅ 判断：{结论判断}。依据：{关键依据}。具体：{必要数值}
```

**示例**：
```
✅ 判断：近 7 天订单执行情况正常。依据：完工率 92.3%，无逾期订单。具体：12 张订单中 11 张已完工，1 张在制中
```

### 12.4 异常结论格式（规范 4.5-4）

句式：**`异常对象 + 异常表现 + 影响/建议`**

使用场景：数据异常、数据不足、业务异常、逻辑冲突、超出预期、存在风险时必须输出。

```
⚠️ 异常对象：{对象名称}。异常表现：{具体异常描述}。影响：{影响范围}。建议：{处理建议}
```

**示例**：
```
⚠️ 异常对象：PO20260701003。异常表现：已超完工日期 5 天仍未完工。影响：直接影响下游车间排产计划。建议：立即确认生产进度，必要时调整计划日期
```

### 12.5 禁止项（规范 4.5-5）

- ❌ 不得把业务摘要和核心结论混用（摘要=字段罗列，结论=分析判断）
- ❌ 不得在没有数据依据的情况下输出判断性结论
- ❌ 结论中不得出现"可能""大概""应该"等不确定词（除非结论本身就是概率性的）
- ❌ 正常结论和异常结论不得使用相同格式

## 十三、四种业务模板固定骨架（P1）

### 13.1 业务单据结构（规范 5.1）

**固定区块顺序**：`引言 → 业务摘要 → 业务详情 → 建议与追问`

| 区块 | 内容 | 备注 |
|------|------|------|
| 引言 | 状态/动作 + 来源 + 对象 + 结果 | 必显 |
| 业务摘要 | 无序列表罗列关键字段（2~7 项） | 必显 |
| 业务详情 | 会话区只展示关键字段，完整单据引导至右侧预览区 | 必显 |
| 建议与追问 | 后续操作引导 | 必显 |

**会话区约束**：单据的完整行项目/明细表/长文本不得在会话区展示，应引导至右侧预览区。

### 13.2 业务查询结构（规范 5.2）

**固定区块顺序**：`引言（必备）→ 核心结论 → 业务详情 → 建议与追问（必备）`

| 区块 | 内容 | 备注 |
|------|------|------|
| 引言 | 句式统一 | 必备 |
| 核心结论 | 正常/异常结论 | 有重点/异常/风险时必须 |
| 业务详情 | 概览统计 → 异常表格 → 明细表格 | 按需 |
| 建议与追问 | 后续操作引导 | 必备 |

**风险前置规则**：当存在风险/异常时，异常关注位于业务详情之前（即：引言 → 核心结论 → **异常关注** → 概览统计 → 明细）。

有分页时，分页提示紧跟明细表格。

### 13.3 分析结构（规范 5.3）

**固定区块顺序**：`引言（必备）→ 核心结论（必备）→ 分析详情 → 建议与追问（必备）`

| 区块 | 内容 | 备注 |
|------|------|------|
| 引言 | 数据来源 + 时间范围 + 分析对象 | 必备 |
| 核心结论 | 正向或异常结论 | 必备 |
| 分析详情 | 最多展示二级标题 | 按需 |
| 建议与追问 | 后续动作引导 | 必备 |

分析详情中，二级标题不得再嵌套更深层级。

### 13.4 方案推荐结构（规范 5.4）

**固定区块顺序**：`引言（必备）→ 推荐结论（必备）→ 判断依据 → 备选方案对比 → 业务风险 → 建议与追问`

| 区块 | 内容 | 备注 |
|------|------|------|
| 引言 | 根据条件/规则 + 为对象 + 推荐方案 | 必备 |
| 推荐结论 | 首选方案和核心依据，必须先给出 | 必备 |
| 判断依据 | 来自已知数据/业务规则/用户输入 | 必显 |
| 备选方案对比 | 至少 2 个备选方案，需说明差异 | 必显 |
| 业务风险 | 各方案的风险提示 | 按需 |
| 建议与追问 | 确认首选方案或进一步筛选 | 必备 |

## 十四、业务摘要规范（P2）

### 14.1 展示位置（规范 4.3-1）

业务摘要位于**引言之后**，单据明细/结果明细/操作按钮或后续说明之前。

若同时有核心结论，位置顺序为：引言 → 核心结论 → 业务摘要 → 业务详情。

### 14.2 展示形式（规范 4.3-2）

使用无序列表罗列关键字段：
- 字段名可加粗
- 字段值不默认加粗（仅关键金额、风险等级等例外情况可加粗值）

### 14.3 极值规则（规范 4.3-3）

- 业务摘要建议 **2～7 项**
- 只有 1 项时，改为普通句（复用 v2.1.0 单列表项转普通句逻辑）
- 超过 7 项时，筛选最关键的 7 项，其余放入业务详情

### 14.4 空值规则（规范 4.3-4）

生单场景（新建单据/申请）时，应在关键字段后标注"待补充信息"。

```
**一、业务摘要**

• **单据类型**：采购申请单
• **申请部门**：生产部
• **预计金额**：待补充信息
• **需求日期**：待补充信息
```

### 14.5 禁止项（规范 4.3-5）

- ❌ 禁止写成核心结论（摘要=字段罗列，不是分析判断）
- ❌ 禁止堆砌所有字段（只列关键字段）
- ❌ 禁止放入行项目/明细表/长文本

## 十五、追问与建议规范（P2）

### 15.1 使用场景（规范 4.4-1）

- AI 输出结论后需用户补充细节、澄清条件、选择分支
- 存在明确的后续操作路径

### 15.2 展示位置（规范 4.4-2）

追问与建议**必须位于 AI 输出结论会话的最后位置**，在所有业务内容之后。

### 15.3 标准引导话术（规范 4.4-3）

| 类型 | 引导话术 |
|------|---------|
| 追问 | "你可能还想了解：…" |
| 建议 | "你可以继续处理：…" |

### 15.4 动作词规则（规范 4.4-4）

操作列表中：
- 每个动作的核心动词**必须加粗并以「」包裹**
- 建议 2~5 项（只有 1 项时改为普通句）

**示例**：
```
你可以继续处理：

• **「发起审核」**：对选中的 3 张订单发起部门审核流程
• **「调整日期」**：修改订单 PO20260701003 的计划完工日期
```

## 二十、Emoji 基础规范（P2）

以下规则约束**技能生成内容**中的 emoji 使用。

### 20.1 可用场景（唯一允许集）

| 场景 | emoji | 示例 |
|------|-------|------|
| 风险、异常、错误、需确认的高风险动作 | ⚠️ | `⚠️ 异常对象：PO2026...` |
| 已完成、成功、正常结论 | ✅ | `✅ 判断：近 7 天执行正常` |

- 除 ⚠️ 与 ✅ 外，技能生成内容中**不使用任何其他 emoji**。
- 若某业务领域确有特殊 emoji 需求，须在对应领域 skill 中**显式声明**后方可使用，否则一律视为违规。

### 20.2 使用约束

- Emoji 必须位于文本左侧（标题 / 正文均以 emoji 开头，不得置于句尾或穿插）。
- Emoji **不得替代文字**：⚠️ 仅作风险/异常标记，必须同时给出文字说明（如"异常对象：…"），不得只显示 ⚠️。
- 保持 B 端专业感，禁止使用 🤯😱💀🔥🎉🥳 等强情绪 / 娱乐化 emoji。
- 代码层已做白名单拦截：`_validate_emoji()` 仅放行 ⚠️ / ✅，其余一律过滤为空。

### 20.3 与其他规范的边界

- 一级标题不再附加 emoji 前缀（见第一节，原标题 emoji 映射已废弃）。
- 状态仅显示中文名称，不再附加彩色灯 emoji（见第五节，原状态灯映射已废弃）。
- 标签（Tag）语义色仍按第十九节对齐 BIP，与 emoji 互不替代。
